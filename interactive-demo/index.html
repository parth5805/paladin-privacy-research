Data segregation

Two layers of separation live inside one shared network.

Within a tenant

Privacy groups

Each private contract sits in its own privacy group. The members list controls visibility. Unlimited groups per Paladin node.

Across tenants

Node membership

Different tenants get different Paladin nodes. Non-member nodes never receive plaintext state — Paladin's transport layer enforces cryptographic isolation.

From public observers

Opaque commitments

Only opaque UTXO commitments hit the base Besu chain. Contract arguments, return values, and events never touch it.

Node hand-over (future migration)

If a tenant needs to leave the shared platform, their Paladin node can be:

  • Transferred to the tenant's own infrastructure. State replicates via reliable transport. Base-chain references stay valid.
  • Retired — removed from privacy group membership, keys revoked, pod dropped.
  • Cloned to backup — snapshot the DB before archival for regulatory retention.
Important limit today
Sub-node isolation (multiple tenants sharing one Paladin node with cryptographic separation) is on the roadmap, not shipped. Today the isolation unit is the Paladin node. Any identity resolvable on a member node can read/write the group's state.

Should we put an L2 in front of Besu?

Layer-2 rollups solve throughput and cost, not privacy. Combine them with Paladin only when the base workload actually demands it.

Use L2 when

  • Public-tx throughput exceeds Besu's ~100–200 TPS ceiling
  • Public gas cost matters (rare in a permissioned Besu but relevant on public L1s)
  • You need cross-ecosystem interop with a public L2

Skip L2 when

  • Private-transaction volume dominates (all confidential work already happens in Paladin, not on the chain)
  • Predictable throughput matters more than peak TPS
  • Operational simplicity is a stronger driver than headline capacity

Consideration
A rollup adds settlement delay and a new operational component. In a permissioned Besu, most consolidation projects do not need one — Besu handles the volume when validators are sized correctly.

The one scenario infrastructure cannot save you from
If every member node of a privacy group loses its DB at the same time, plaintext is unrecoverable. The base chain has only opaque commitments. For projects where this is material, application-managed off-Paladin encrypted backups are the answer.

The 3f+1 sizing pays off here
With 7 validators and f=2, up to 2 can be out simultaneously without stalling consensus. Comfortable room for rolling upgrades and unexpected failures.

Release patterns that don't leak across tenants

Every pattern below preserves the guarantee: a change to tenant A's stack cannot break tenant B's.

Canary tenant

Nominate one non-production tenant that always receives platform upgrades first. Failures are contained.

Blue / green privacy groups

Deploy the new contract into a new privacy group with the same members. Migrate state, verify, cut over.

Feature flags in contracts

Behaviour changes gated by governance-controlled flags. Roll out per tenant, roll back instantly.

Shadow reads

New logic runs alongside old, results compared off-chain. Only cut over when parity is proven.

Isolation guarantees during a release

  • Application contract upgrades are tenant-scoped. No other tenant's contract addresses change.
  • Platform upgrades are announced with a maintenance window. Tenants can pause writes if needed.
  • Rollback for smart contracts is never a state rewind — it is a governance action that deploys the previous version and migrates forward.
  • Cross-tenant atomic transactions are pinned to specific base-chain contract versions — upgrading the app does not invalidate historical bundles.

The three options at a glance

Shared (Option A)

One shared Paladin node for internal-only projects that already trust each other. Cheapest. Application-layer ACLs required.

Hybrid (Option B) — default

Shared Besu, dedicated Paladin nodes per project. Cryptographic isolation between projects at low ops cost.

Dedicated (Option C)

Separate Besu network per project. Strongest isolation. Reserved for regulator-segregated or ultra-sensitive workloads.

SharedChain — what this demo is

A single-file interactive explainer of a shared-blockchain platform pattern using Hyperledger Besu + Paladin. Configure the topology on the left, click any element in the diagram to inspect it, and read the tabs for design context.

Base layer

Hyperledger Besu with 3f+1 validators for BFT consensus. Shared across all tenants.

Privacy layer

Hyperledger Paladin. Adds ephemeral EVMs, privacy groups, and cross-domain atomicity on top of Besu.

Tenants

Independent projects — each gets its own Paladin nodes, its own privacy groups, its own governance.

Interoperability

Atomic bundling on the base chain lets separate privacy groups transact together without leaking state.

Terminology

TermMeaning
BesuThe base EVM chain. Public-within-the-network, opaque commitments only.
PaladinPrivacy layer on top of Besu. Runs private EVMs (Pente), tokens (Noto, Zeto).
Privacy groupAn agreement between a set of Paladin nodes to share confidential state.
Ephemeral EVMA fresh in-memory Besu EVM spun up per private transaction, then discarded.
EndorsementSigned confirmation from member nodes that a private transaction is valid.
UTXO commitmentOpaque hash that hits the base chain as proof of a private state transition.
3f+1The BFT consensus sizing rule. With f failures tolerated, you need 3f+1 validators.
