Data segregation

Two layers of separation live inside one shared network.

Within a tenant

Privacy groups

Each smart contract sits in its own privacy group. Members list controls visibility. Unlimited groups per node.

Across tenants

Node membership

Different tenants get different Paladin nodes. Non-member nodes never receive plaintext state — cryptographic isolation.

From public observers

On-chain commitments

Only opaque UTXO commitments hit Besu. Contract arguments, return values, events — none of it goes on the base chain.

Node hand-over (future migration)

If a tenant leaves the shared platform, their Paladin node can be:

  • Transferred to the tenant's own infrastructure. State replicates via reliable transport. Base chain reference remains valid.
  • Retired — remove from privacy group membership, revoke keys, drop the pod.
  • Cloned to backup — snapshot DB before archival for regulatory retention.
Important limit today
Sub-node isolation (multiple tenants sharing one Paladin node) is on the roadmap, not shipped. Today the isolation unit is the node. See the decision panel for what this means in practice.

Should we put an L2 in front of Besu?

Layer-2 rollups solve throughput and cost, not privacy. Combine them with Paladin only when the base workload actually demands it.

Use L2 when

  • Public-tx throughput exceeds Besu's ~100–200 TPS ceiling
  • Public gas cost matters (rare in a permissioned Besu but relevant on public L1s)
  • You need cross-ecosystem interop with a public L2

Skip L2 when

  • Private-transaction volume dominates (all confidential work already happens in Paladin, not on chain)
  • Predictable throughput matters more than raw peak TPS
  • Operational simplicity is a stronger driver than headline capacity

Consideration
A rollup adds a settlement delay and a new operational component. In a permissioned Besu network, most consolidation projects do not need one — Besu itself handles the volume when validators are sized correctly.

The one scenario infrastructure cannot save you from
If every member node of a privacy group loses its DB at the same time (rare but possible: bad DR restore across the fleet), plaintext is unrecoverable. Base chain has only opaque commitments. For projects where this is material, application-managed off-Paladin encrypted backups are the answer.

The 3f+1 sizing pays off here
With 7 validators and f=2, up to 2 can be out simultaneously without stalling consensus. That gives comfortable room for rolling upgrades and unexpected failures at the same time.

Release patterns that don't leak across tenants

Every pattern below preserves the guarantee: a change to tenant A's stack cannot break tenant B's.

Canary tenant

Nominate one non-production tenant that always receives platform upgrades first. Failures are contained to it.

Blue / green privacy groups

Deploy the new contract into a new privacy group with the same members. Migrate state, verify, cut over, deprecate old group.

Feature flags in contracts

Behaviour changes gated by governance-controlled flags. Roll out per tenant, roll back instantly if issues arise.

Shadow reads

New logic runs alongside old, results compared off-chain. Only cut over when parity is proven.

Isolation guarantees during a release

  • Application contract upgrades are tenant-scoped. No other tenant's contract addresses change.
  • Platform upgrades are announced with a maintenance window. Tenants can pause their own writes if needed.
  • Rollback for smart contracts is never a state rewind — it is a governance action that deploys the previous version and migrates forward.
  • Cross-tenant atomic transactions are pinned to a specific base-chain contract version — upgrading the app does not invalidate historical bundles.

What the three options look like

Shared (Option A)

One shared Paladin node for all internal projects that already trust each other. Cheapest. Application-layer ACLs required.

Hybrid (Option B) — default

Shared Besu, dedicated Paladin nodes per project. Cryptographic isolation between projects at low ops cost.

Dedicated (Option C)

Separate Besu network per project. Strongest isolation. Reserved for regulator-segregated or ultra-sensitive workloads.

SharedChain — What this demo is

A single-file interactive explainer of a shared-blockchain platform pattern using Hyperledger Besu + Paladin. Configure the topology on the left, watch the network respond, read the tabs for context on the design decisions.

Base layer

Hyperledger Besu with 3f+1 validators for BFT consensus. Shared across all tenants.

Privacy layer

Hyperledger Paladin. Adds ephemeral EVMs, privacy groups, and cross-domain atomicity on top of Besu.

Tenants

Independent projects — each gets its own Paladin nodes, its own privacy groups, its own governance.

Interoperability

Atomic bundling on the base chain lets separate privacy groups transact together without leaking state.

Terminology cheat sheet

TermMeaning
BesuThe base EVM chain. Public-within-the-network, opaque commitments only.
PaladinPrivacy layer on top of Besu. Runs private EVMs (Pente), tokens (Noto, Zeto).
Privacy groupAn agreement between a set of Paladin nodes to share confidential state.
Ephemeral EVMFresh in-memory Besu EVM spun up per private transaction, then discarded.
EndorsementSigned confirmation from member nodes that a private transaction is valid.
UTXO commitmentOpaque hash that hits the base chain as proof of a private state transition.
3f+1The BFT consensus sizing rule. With f failures tolerated, you need 3f+1 validators.
